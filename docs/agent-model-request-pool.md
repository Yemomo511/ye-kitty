# Agent 模型请求池说明

## 背景

当前 QQ Agent Harness 通过单组 `OPENAI_API_KEY`、`OPENAI_BASE_URL` 和 `YE_KITTY_AGENT_MODEL` 调用底层模型。这个形态适合最小闭环，但在群聊短时间出现大量消息、多个会话同时触发智能体，或模型服务出现 429 限流时，所有请求都会集中打到同一个模型入口。

模型请求池的目标是把“模型理解能力”从具体模型配置中抽离出来。Agent Harness 只表达“我需要一次结构化模型决策”，不直接关心请求会落到哪个 `baseURL`、哪个模型、当前模型是否退避或排队。

## 设计定位

模型请求池是 Agent Runtime 与 OpenAI 兼容模型服务之间的调度层，负责：

- 模型路由：从多个模型节点中选择一个可用节点处理请求。
- 并发控制：每个模型节点独立限制同时运行的请求数量。
- 请求间隔：同一模型节点两次真实请求之间保持最小间隔。
- 429 退避：模型节点遇到限流后进入指数退避，避免继续放大限流。
- 失败降级：请求超过重试或队列等待预算后，向上层返回可识别失败。
- 观测日志：记录模型选择、排队耗时、请求耗时、429、退避和失败原因。

## 推荐配置

第一版建议从单模型配置平滑迁移到模型节点列表。每个模型节点包含独立的访问地址、模型名、并发和限流参数。

```json
{
  "models": [
    {
      "id": "main-chat-1",
      "baseURL": "https://api.example.com/v1",
      "apiKey": "sk-xxx",
      "model": "gpt-4.1-mini",
      "maxConcurrency": 3,
      "minIntervalMs": 2000,
      "maxRetries": 3,
      "backoff": {
        "initialMs": 2000,
        "maxMs": 60000,
        "multiplier": 2
      }
    }
  ]
}
```

字段说明：

| 字段             | 说明                                                    |
| ---------------- | ------------------------------------------------------- |
| `id`             | 模型节点唯一标识，用于日志、路由和问题定位。            |
| `baseURL`        | OpenAI 兼容服务地址。                                   |
| `apiKey`         | 当前模型节点使用的密钥。                                |
| `model`          | 当前模型节点的模型名称。                                |
| `maxConcurrency` | 当前模型节点允许的最大并发请求数，默认建议为 3 或 4。   |
| `minIntervalMs`  | 当前模型节点两次发起真实请求的最小间隔，默认建议 2 秒。 |
| `maxRetries`     | 单次请求遇到可重试错误时的最大重试次数。                |
| `backoff`        | 429 或临时不可用时的指数退避参数。                      |

## 请求调度规则

每个模型节点维护自己的运行状态：

- `queue`：等待该模型节点处理的请求队列。
- `activeCount`：当前正在执行的请求数量。
- `nextAvailableAt`：受 `minIntervalMs` 控制的下一次可请求时间。
- `backoffUntil`：遇到 429 后暂停接收新请求的截止时间。

请求只有同时满足以下条件才会真正发出：

```text
activeCount < maxConcurrency
当前时间 >= nextAvailableAt
当前时间 >= backoffUntil
请求未超过自身 TTL
```

如果某个模型节点触发 429，请求池优先读取服务端返回的 `Retry-After`。如果没有该字段，则按 `initialMs * multiplier` 递增等待时间，并限制在 `maxMs` 以内。退避状态挂在模型节点上，而不是只挂在单个请求上；这样后续请求不会继续打向已经限流的节点。

## Harness 接入方式

第一版接入后，调用方向应保持为：

```text
AgentRuntimeHarness
  -> AgentRunnerPort
  -> ModelRequestPool
  -> ModelWorker
  -> OpenAI Compatible Client
```

`AgentRuntimeHarness` 仍然只负责循环、工具、Skill、权限和最终决策协议。`AgentRunnerPort` 仍然表示“请求一次结构化模型决策”。模型请求池只处理模型调用调度，不读取 Skill、不执行工具、不决定是否回复 QQ。

## 降级建议

模型请求失败后，上层应根据触发来源选择降级方式：

- 私聊或明确 @：返回中文短降级回复，提示稍后再试。
- 群聊随机窗口：静默丢弃，避免延迟回复打断群聊。
- 回复后计数器触发：如果请求过期，直接放弃本轮触发，等待下一轮节奏门控。
- 后台任务：标记失败并等待下一次调度，不在聊天链路中阻塞。

## 后续演进

第一版只解决 Agent Harness 的结构化决策请求。后续可以继续补充：

- 会话级单飞和消息合并，避免同一群聊同时制造多次模型请求。
- 成本和能力路由，让便宜模型处理轻量判断，高能力模型处理复杂推理。
- 模型健康评分，根据成功率、延迟和 429 频率动态调低节点权重。
- RunTrace 持久化，记录模型节点、成本、耗时、重试和失败原因。
- 控制面展示，支持查看模型节点状态、队列长度、退避时间和近期错误。
