## 叶猫猫服务层

社交服务设置统一的消息总线，并给予LLM处理完数据后，对社交进行响应处理。

## 规则

- 修改项目架构时，需要及时更新 `src/ARCHITECTURE.md` 文件。
- 共享结构体、接口和类型统一放在 `src/shared/types`。
- 模板方法模式和策略模式按需使用，不建立统筹所有服务的统一抽象类或统一策略注册器。
- 某个服务内出现稳定流程复用时，优先在该服务的 `application` 或 `domain` 中建立局部抽象类。
- 某个服务内出现多种可替换算法或决策路径时，优先在该服务的 `ports` 或 `domain` 中建立局部策略接口。
- 只有抽象、模板或策略被多个服务稳定复用时，才允许上沉到 `src/shared`。
- 包内局部运行命令统一放在包级 `scripts/` 目录下，避免在业务源码目录中继续新增 `bin/` 启动入口。

## 测试用例
测试的核心目的在于客观的评估，因此编写测试代码时，应该在计划阶段就提出测试用例，书写具体的测试代码时，应该严格按照计划提出的测试用例进行，不允许迎合代码去写测试用例来偷懒。
- 在开发任何新模块时，先提出测试用例/测试方案，并完成TDD红灯代码，然后完成具体的实现代码。
- 测试用例/测试方案应该覆盖所有可能的场景，包括边界场景和异常场景。
- 测试用例/测试方案应该符合TDD的规范，即先编写测试用例，然后编写实现代码。

### 大模型的测试
大模型的测试较为复杂，在传统的测试中，"不变性" 是一个重要的概念，即在给定的输入下，测试结果的输出是确定的。LLM 大语言模型的输出往往具有完全的不确定性，因此我们不应干涉大模型的输出内容，而更应该考虑其结构性调用。例如
``` markdown
1. 测试大模型是否能够正确输出定义的结构
prompt: "你后续的所有回复都必须使用以下JSON结构来进行回复 {...}"
input: 你好
output: {tools: "reply", content: "你好"}

2. 测试Agent是否拥有调用工具/Skill的能力

- 测试1： 显式使用工具名称/Skill名称调用
输入: "请使用工具 'get_weather' 来获取天气信息，并告诉我北京天气怎么样"
检验1: 验证Agent的第一轮响应的output的结构的tools是否包含"invoke_tool", tool_name 是否等于 "get_weather"
校验2: 验证Agent的第二轮响应的output的结构的tools是否包含"reply"。Content 不检验

- 测试2： 隐式使用工具名称/Skill名称调用
目的: 用户想要写一个markdown文档，能否触发情景为“如何来写一个markdown文档”的`write-markdown` Skill
输入: "帮我写一个Markdown文档，说明一下整个大前端的技术架构"
检验1: 验证Agent的第一轮响应的output的结构的tools是否包含"invoke_skill", skill_name 是否等于 "write-markdown"
校验2: 验证Agent的第二轮响应的output的结构的tools是否包含"reply"。Content 不检验
```

> PS： 例子中的结构体字段仅作为示例，仅提供一种思考方式，**不要在任何实现结构体字段时使用例子中的名称**
