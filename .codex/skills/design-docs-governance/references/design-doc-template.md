# 子设计文档模板

子设计文档负责承载具体设计方案。它需要让产品、开发、设计和 Agent 在同一份文档中达成一致：为什么做、怎么做、边界在哪里、如何验收。

## 推荐结构

```markdown
# {功能或模块名称} 设计方案

## 背景

{说明问题来源、用户场景、业务上下文或技术背景。}

## 目标

- {目标一}
- {目标二}

## 非目标

- {本次明确不做的事情}

## 角色共识

- 产品关注：{用户价值、使用流程、边界}
- 设计关注：{体验、信息结构、反馈方式}
- 开发关注：{模块边界、接口、数据流、风险}
- Agent 关注：{需要遵守的文档、代码、测试和进度同步规则}

## 整体设计

{说明模块划分、核心流程、数据流或交互流。必要时使用 Mermaid 图。}

## 设计思想

{说明为什么这样设计，包括关键取舍、复用边界、暂不抽象的原因或后续扩展点。}

## 关键实现

### 模块一：{名称}

- 入口：`{文件、命令、路由或操作入口}`
- 职责：{模块职责}
- 重要细节：{关键实现细节}
- 边界：{不负责什么}

### 模块二：{名称}

- 入口：`{文件、命令、路由或操作入口}`
- 职责：{模块职责}
- 重要细节：{关键实现细节}
- 边界：{不负责什么}

## 数据与接口

| 名称         | 方向                 | 说明                   |
| ------------ | -------------------- | ---------------------- |
| {数据或接口} | {输入 / 输出 / 双向} | {字段、约束或调用关系} |

## 风险与边界条件

| 风险     | 触发条件   | 处理方式         |
| -------- | ---------- | ---------------- |
| {风险点} | {何时发生} | {规避或降级方式} |

## 测试方案

- 单元测试：{覆盖点}
- 集成测试：{覆盖点}
- 端到端或手动验证：{验证步骤}
- 回归范围：{需要确认不受影响的路径}

## 验收方式

- 产品验收：{可观察结果}
- 设计验收：{体验或视觉标准}
- 开发验收：{测试、类型、Lint、构建或运行标准}
- Agent 验收：{文档、代码、测试、Task 状态是否一致}

## 唯一入口

- 使用入口：{用户或业务入口}
- 代码入口：`{文件或模块路径}`
- 测试入口：`{测试命令或测试文件}`
- 文档入口：`{本文档路径}`

## 进度记录

| 日期         | 状态   | 说明         |
| ------------ | ------ | ------------ |
| {YYYY-MM-DD} | {状态} | {进展或结论} |
```

## 合格标准

- 能看出整体模块和设计思想。
- 能定位关键实现入口和重要细节。
- 能说明为什么这样做，而不是只描述做了什么。
- 有最终测试方案、验收方式和唯一入口。
- 和 `Task.md` 的状态、拆分、入口保持一致。
