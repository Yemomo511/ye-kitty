# 状态同步规则

本文件用于判断 `design-docs/Task.md` 和子设计文档中的状态如何流转。

## 状态定义

| 状态   | 含义                                         | 允许进入条件             |
| ------ | -------------------------------------------- | ------------------------ |
| 未开始 | 已确认要做，但还没有形成设计或实现动作       | 有明确目标或待办         |
| 设计中 | 正在梳理方案、边界、入口和验收方式           | 已开始写设计文档         |
| 开发中 | 已进入代码实现、配置调整或工程落地           | 设计方案足够支撑实现     |
| 待验收 | 实现已完成，等待测试、产品或设计确认         | 已有测试结果或可验证入口 |
| 已完成 | 设计、实现、测试和验收均已闭环               | 有完成依据和最终入口     |
| 阻塞   | 缺少关键输入、权限、环境或决策，无法继续推进 | 写清阻塞原因和下一步     |
| 暂停   | 主动延后，不再作为当前推进项                 | 写清暂停原因和恢复条件   |
| 废弃   | 明确不再采用该方案或拆分项                   | 写清废弃原因和替代路径   |

## 同步时机

- 新建大功能迭代时，更新 `Task.md` 的目标、拆分和初始状态。
- 新增、删除或合并子设计文档时，更新 `Task.md` 的设计拆分表。
- 完成设计方案时，把对应项从 `设计中` 更新为 `开发中` 或 `待开发` 口径；如果项目没有 `待开发` 状态，保持 `设计中` 并写清下一步。
- 完成代码实现时，更新对应子文档的关键实现、唯一入口和进度记录。
- 完成测试或验收时，更新测试方案结果、验收方式结论和 `Task.md` 状态。
- 发现实现偏离设计时，记录漂移点，并说明选择修代码还是修文档。

## 完成依据

标记为 `已完成` 前，至少满足：

- `Task.md` 有对应拆分项，并指向正确子设计文档。
- 子设计文档包含整体设计、设计思想、关键实现、测试方案、验收方式和唯一入口。
- 代码入口、测试入口或操作入口可定位。
- 相关测试、检查或手动验收结果已记录。
- 没有未解释的阻塞、风险或文档漂移。

## 写法要求

- 状态说明要写事实，不写情绪化判断。
- 进度记录要写“完成了什么”和“依据是什么”。
- 阻塞记录要写“缺什么”“影响什么”“下一步找谁或做什么”。
- 变更记录要写“为什么改”，方便后续回滚或复盘。
